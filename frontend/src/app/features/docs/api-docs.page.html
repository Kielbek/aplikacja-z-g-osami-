Przewodniki

#Długie teksty

Do 5 000 znaków używaj syntezy synchronicznej — połączenie pozostaje otwarte do końca generowania. Dłuższe teksty wysyłaj jako zadanie w tle:

  1. Utwórz zadanie z nagłówkiem Idempotency-Key i (najlepiej) callback_url.
  2. Zaczekaj na webhook job.succeeded albo odpytuj stan zadania co kilka sekund.
  3. Pobierz nagranie w ciągu 7 dni.

Zadania w tle ustępują na karcie graficznej pierwszeństwa syntezie synchronicznej, więc czas oczekiwania zależy od obciążenia. Tekst jest dzielony po akapitach i zdaniach, a części łączone z krótką przerwą — nagranie brzmi jak jedna całość.

#Webhooki

Jeśli zadanie ma callback_url, po jego zakończeniu wyślemy POST ze zdarzeniem job.succeeded lub job.failed. Pole data zawiera pełny obiekt zadania. Adres musi używać https:// i wskazywać serwer publiczny.

Weryfikacja podpisu

Nagłówek Narrivy-Signature ma postać t=<czas unix>,v1=<podpis>. Podpis to HMAC-SHA256 z tekstu t + "." + surowa treść; kluczem jest sekret webhooków z Ustawienia → API. Odrzucaj zdarzenia z błędnym podpisem lub starsze niż 5 minut. Licz podpis z surowych bajtów treści — nie z ponownie zserializowanego JSON-a.

Ponowienia

Odpowiedz kodem 2xx w ciągu 10 sekund — długie przetwarzanie wykonuj po odpowiedzi. W przeciwnym razie ponowimy wysyłkę po 10 s, 1 min, 5 min i 30 min (łącznie 5 prób). Zdarzenie może wyjątkowo dotrzeć dwa razy — rozpoznasz je po data.id.

#Pauzy, wymowa i styl

  • Pauzy: wstaw w tekście [pauza 1s], [pauza 1.5s] lub [pauza 500ms] — w tym miejscu powstanie cisza o dokładnej długości. Znaczniki nie są liczone jako znaki.
  • Wymowa: słownik wymowy z Twojego konta (Ustawienia → Słownik wymowy) działa także w API — dodaj tam nazwy, skróty i nazwiska.
  • Styl i emocje: style opisuje sposób mówienia słowami, emotion nadaje emocję. Gdy pominiesz oba, głos użyje swojego default_instruction (np. wariant „Relaks”).
  • Powtarzalność: ten sam tekst, głos, parametry i seed dają to samo nagranie — możesz je buforować.

#Ponawianie i idempotencja

  • Ponawiaj tylko błędy oznaczone w tabeli błędów jako „tak” — odczekaj tyle sekund, ile podaje Retry-After, a gdy go brak, stosuj odstęp wykładniczy (1 s, 2 s, 4 s…).
  • Błędów 4xx z innymi kodami nie ponawiaj — popraw żądanie.
  • Przy tworzeniu zadań zawsze wysyłaj Idempotency-Key i używaj tego samego klucza przy każdej próbie — zadanie (i opłata) powstanie tylko raz.

#Bezpieczeństwo kluczy

  • Wywołuj API wyłącznie z własnego serwera. API celowo nie obsługuje wywołań z przeglądarki (CORS), a sesja zalogowanego użytkownika nie daje dostępu do /v1.
  • Przechowuj klucz w zmiennej środowiskowej lub menedżerze sekretów, nie w repozytorium.
  • Używaj osobnego klucza dla każdej aplikacji — przy każdym kluczu widać zużycie, a w razie wycieku unieważnisz tylko jeden.
  • Klucz, który mógł wyciec, od razu unieważnij w Ustawienia → API i utwórz nowy. Unieważnienie działa natychmiast.
  • Głosów sklonowanych używaj tylko w zakresie zgody właściciela głosu złożonej przy klonowaniu.

#Wersje i zmiany

Wersja jest częścią adresu (/v1). W ramach v1 dodajemy tylko zmiany zgodne wstecz: nowe endpointy, nowe opcjonalne pola żądań, nowe pola odpowiedzi i nowe kody błędów — Twój kod powinien ignorować nieznane pola odpowiedzi. Zmiany niezgodne wstecz trafią do v2, a o wycofaniu v1 poinformujemy z wyprzedzeniem.
